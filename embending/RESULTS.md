# Результаты тестов векторного поиска (MFC Тульской области)

Дата: 2026-09-11 · Конфигурация: PostgreSQL 17 + pgvector 0.8.6 (Docker, localhost:5434) · Корпус: 732 услуги из `data/services_for_llm.json` · Железо: Apple Silicon (MPS)

## Схема и пайплайн

- Таблица `services (id, title, department, content, embedding vector(1024))`, индекс HNSW `vector_cosine_ops`.
- EXPLAIN подтверждает `Index Scan using services_embedding_idx`.
- Контроль качества эмбеддингов: self-cosine = 1.000 (L2-нормализация корректна), средний косинус с случайными документами = 0.336 (нормальная сепарация).
- Скрипты: `build_index.py` (индексация), `search.py` (поиск), `eval_bench.py` (бенчмарк), `eval_models.py` (сравнение моделей).

## Методология бенчмарка

16 реалистичных запросов «от лица гражданина» (разговорный язык) с вручную размеченным ground truth по ID услуг. Включены сложные пары: внутренний vs загранпаспорт, брак vs развод, пенсия vs военная пенсия. Метрики: Recall@1/3/5, MRR по полному корпусу из 732 документов.

Примечания:
- «Giga/Qwen + Instruct» — запрос кодируется с префиксом `Instruct: {задача}\nQuery: {вопрос}`, документы — без него. BGE-M3 — оба без префиксов (по рекомендациям модели).
- Строки 1 и 4–5, 7 измерены на контенте с `documentsText`; строки 2–3, 6 — на контенте без него.

## Анализ промахов лучшей модели (Giga-480M + Instruct)

| Запрос | Ранг | Причина |
|---|---|---|
| «оформить паспорт для поездок за рубеж» | 3 | два почти-дупликата (внутр./загран паспорт, один отдел) — проблема данных, не модели |
| «хотим подать заявление чтобы расписаться» | 7 | разговорная омонимия «расписаться» ≈ «подписаться» |
| «потерял российский паспорт восстановить» | 6 | в корпусе нет слова «потерял» — лексический разрыв |

BGE-M3 на «расписаться» падает в ранг 15–45 — заметно хуже.

## Ключевые выводы

1. **Лучший измеренный конфиг: Giga-480M + Instruct-префикс + documentsText в контенте (R@1 0.81, MRR 0.853).**
2. Префикс `Instruct:` обязателен: +19 п.п. R@1 (0.62 → 0.81).
3. `documentsText` полезен для Giga: удаление обваливает R@1 0.81 → 0.50 (списки документов различают похожие услуги); для BGE-M3 почти нейтрален.
4. **BGE-M3 не является апгрейдом** — уступает Giga-480M по R@1/MRR на этих данных (−19/−8 п.п.). Плюсы: лучше R@3/R@5 (без documentsText), поддерживает sparse/ColBERT-векторы одной моделью, работает без `trust_remote_code`.
5. Qwen3-Embedding-0.6B (~тот же размер) — на уровне Giga-480M (R@1 0.81, MRR 0.856), тоже валидный кандидат.
6. Ошибка «внутренний vs загранпаспорт» не лечится заменой dense-модели — это дубликаты в данных; лечится reranker'ом, гибрид-поиском или дедупликацией.

## Рекомендация

Вернуться к **Giga-480M + Instruct + documentsText**; дальнейший рост качества искать в пайплайне, а не в модели:
1. reranker (cross-encoder / LLM) вторым этапом по top-10;
2. гибрид с лексическим поиском (`tsvector` + RRF) против разговорных омонимов и разрывов лексики;
3. дедупликация карточек «внутренний/загранпаспорт» или раздельные эмбеддинги title + max-pool скоринг.

BGE-M3 оставлять в проде только если нужен sparse-канал (гибрид) из одной модели без отдельного BM25.
