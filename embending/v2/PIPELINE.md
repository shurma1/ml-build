# Конвейер поиска услуг МФЦ

Поиск услуги по расшифровке разговора оператора с посетителем. Корпус — 732 карточки
услуг МФЦ Тульской области, свёрнутые в 321 тип. Группировка хранится в
`data/type_map.json` и правится руками; порождает её `tools/remap_type_keys.py`.

---

## Главная идея

Задача не «найти похожий текст», а три разные задачи, которые нельзя решать одним
вектором:

| задача | чем решается |
|---|---|
| намерение → **тип услуги** | плотный поиск, 321 класс |
| тип → **конкретная карточка** | структурный фасет «муниципалитет», 26 значений |
| карточка → **положена ли клиенту** | таблица предикатов, проверяется ПОСЛЕ поиска |

445 карточек из 732 — это одна и та же муниципальная услуга, размноженная по 26
муниципалитетам. Пока муниципалитет лежит внутри вектора, порядок внутри такой
группы решает разрыв косинуса 0.002, то есть шум. Поэтому он вынесен в колонку.

---

## Схема работы

```
расшифровка диалога (сегменты VAD)
   │
   │  ratelimit.is_empty_segment — отсев «ага», «понятно»
   ▼
LLM + JSON-грамматика  ──►  признаки
   │   extraction_schema.JSON_SCHEMA   (жёсткие enum: 17 ситуаций, 3 заявителя,
   │   extraction_schema.validate()     8 категорий, 26 МО)
   │   extraction_schema.DialogState    монотонное состояние диалога
   ▼
features.QueryFeatures
   │   intents[1..4]  ─────────────────►  один батч в энкодер
   │   municipality, recipient ────────►  фасеты
   │   facts{age, children, categories}►  проверка права
   ▼
dialog.DialogSearch.search()
   ├─ mE5-large-instruct  →  N векторов запроса   (~114 мс CPU, батч почти бесплатен)
   ├─ ЦЕНТРОИД намерений  →  один вектор запроса  (слияние ДО поиска, не после)
   ├─ pgvector HNSW × 1   →  30 кандидатов        (~2 мс)
   ├─ eligibility.check() →  eligible / blocked / unknown + цитата
   └─ clarify.suggest()   →  вопрос по приросту информации, если отрыв top1-top2 мал
   ▼
резолв типа в карточку: МО из признаков → из филиала оператора → иначе список на выбор
   ▼
ответ оператору: список услуг с пометками права + что спросить дальше
```

## Быстрый старт

```bash
export EMB_DB="host=localhost port=5434 dbname=embeddings user=emb password=emb"
export EMB_MODEL="intfloat/multilingual-e5-large-instruct"

python3 v2/build_index.py          # ~35 с: 321 тип + 732 карточки + 114 филиалов
python3 v2/eval/acceptance.py      # 22 проверки, что конвейер собран верно
python3 v2/search.py "потерял паспорт в щекино"
```

### Поиск из кода

```python
import sys; sys.path.insert(0, 'v2')
from dialog import DialogSearch
from features import QueryFeatures

d = DialogSearch()

# вариант 1: признаки от LLM
f = QueryFeatures.from_llm({
    "intents": ["выплата при рождении второго ребёнка", "пособие молодой маме"],
    "life_situation": "Рождение ребенка",
    "recipient": "person",
    "municipality": "Щекинский район",
    "facts": {"age": 22, "children": 2},
})

# вариант 2: ручной ввод оператора — фасеты доберёт газеттир
f = QueryFeatures.from_text("оформить пособие в узловой")

r = d.search(f, k=8)
for x in r["results"]:
    print(x["status"], x["title"], "->", x["service_id"])
for q in r["questions"]:
    print(q["gain_bits"], "бит:", q["question"])

# ответы на наводящие вопросы за диалог
r2 = d.narrow(f, [("выплата", True), ("ребенок", True)], k=8)
```

### Что возвращает `search()`

| поле | |
|---|---|
| `results[].status` | `eligible` / `blocked` / `unknown` |
| `results[].reasons` | причина + **дословная цитата** из регламента |
| `results[].service_id` | карточка, если МО известно |
| `results[].needs_municipality` | иначе — список `available_in` на выбор |
| `questions` | наводящие вопросы, лучший первым, с приростом в битах |
| `missing_facts` | чего не хватило для проверки права |
| `ms`, `ms_embed` | задержка |

### Контекст оператора

```python
d.search(f, branch_id="...")   # район филиала станет МО по умолчанию
```

Приоритет: явный параметр → топоним в запросе → район филиала оператора.

## Что показали замеры

Метрика — по типу услуги, 690 запросов, бутстрап-интервал ±3.5 п.п.

| конфигурация | R@1 | R@10 | MRR |
|---|---|---|---|
| исходный прод: BGE-M3, склейка всех полей, 732 карточки | 0.591 | 0.888 | 0.705 |
| + типы услуг и чистый текст (та же модель) | 0.628 | 0.926 | 0.741 |
| + mE5-large-instruct (и при этом в 1.4× быстрее) | 0.680 | 0.961 | 0.786 |
| + синонимы от LLM | **0.732** | **0.977** | **0.817** |
| + 2 уточняющих вопроса | 0.810 | — | — |
| + 4 уточняющих вопроса | **0.839** | — | — |

Слияние нескольких формулировок одного намерения, 230 групп по три:

| правило | R@1 | MRR |
|---|---|---|
| только первое намерение | 0.748 | 0.829 |
| RRF 3:1:1 (было до сентября) | 0.783 | 0.862 |
| максимум косинуса | 0.791 | 0.869 |
| **центроид векторов запроса** | **0.857** | **0.908** |

RRF переводит оценки в ранги и выбрасывает величину сходства; у e5 все косинусы
лежат в полосе 0.85–0.95, и различия внутри неё информативны. Центроид равен
усреднению косинусов (`mean(q)·d = mean(q·d)` при нормированных документах),
поэтому заодно схлопывает N обращений к индексу в одно.

Проверено и отвергнуто — обе ступени качества не добавляют:

| | R@1 |
|---|---|
| только dense (прод) | **0.732** |
| + гибрид с tsvector, RRF 1:1 всегда | 0.617 |
| + гибрид RRF 5:1 при отрыве < 0.005 | 0.726 |
| + кросс-энкодер bge-reranker-v2-m3, top-10 | 0.687 |
| + он же в сумме с dense по z-оценкам | 0.730 |

Потолок переранжирования при этом 0.977 (идеальная сортировка top-10) — запас
есть, но готовым кросс-энкодером он не берётся.

Задержка, CPU, один поток, кэш пуст:

| | p50 | p95 | p99 |
|---|---|---|---|
| энкодер | 113.7 | 135.2 | 164.7 мс |
| HNSW top-30 | 5.8 | 8.1 | 10.8 мс |
| **весь запрос** | **120.3** | **141.2** | **175.8 мс** |
| тёплый кэш | **≈ 7–9 мс** | | |

Пропускная способность одной машины — **≈15 запросов/с** (упирается в CPU на энкодере;
pgvector сам по себе 2.1 мс). Три формулировки одним батчем стоят ×1.23 от одной, не ×3.

## Уточняющие вопросы

Вопрос выбирается арифметикой по кандидатам, без LLM. Две калибровки, без которых
он вредит:

**Гейт по отрыву** (`clarify.CERTAIN_MARGIN = 0.02`). Отрыв top1−top2 предсказывает
правоту верхней строки:

| отрыв | доля запросов | точность top-1 |
|---|---|---|
| < 0.005 | 25% | 0.446 |
| 0.005–0.010 | 17% | 0.517 |
| 0.010–0.020 | 25% | 0.836 |
| 0.020–0.050 | 29% | 0.980 |
| ≥ 0.050 | 4% | 1.000 |

Выше порога сужать нечего, и вопросы «на сужение» отпадают. Вопросы про ВЕРДИКТ
(`needed`) гейт не трогает: они спрашивают не «какая из услуг», а «положена ли вам
эта». Связка «центроид + 4 вопроса» даёт R@1 0.904 и с гейтом, и без, но 308
вопросов вместо 482.

**Вес переранжирования** (`clarify.RESCORE_WEIGHT = 0.02`). Шкала косинусная:
разброс по пулу из 30 кандидатов — 0.058, отрыв соседних позиций — 0.013. Прежние
0.35 были в шесть раз больше всего разброса, то есть раскладывали список на три
блока вместо того, чтобы двигать кандидатов. При безошибочных ответах разницы нет,
а при ошибочных — есть:

| доля ошибочных ответов | 0% | 15% | 30% |
|---|---|---|---|
| weight 0.35 | 0.816 | 0.623 | 0.462 |
| weight 0.02 | 0.816 | 0.692 | 0.578 |
| не спрашивать вообще | 0.732 | 0.732 | 0.732 |

Ответ приходит из речи через ASR и извлечение, поэтому 0% — не рабочее допущение.

Вопрос несёт форму ответа (`kind`, `options`) и поле `fact`. `fact` обязателен для
вопросов о возрасте, детях и категории: переранжирование ключа `age` не знает, и
без записи в состояние такой ответ не делает ничего.

## Ограничения, которые надо знать

* **Предикаты права не вычитаны человеком.** 363 штуки, сгенерированы LLM, цитаты
  проверены автоматически. Для решения о деньгах этого мало — нужна вычитка.
  Условия есть у 103 типов из 321; остальные проверяются только по виду заявителя.
* **Всё измерено на синтетических запросах.** Живого лога нет. Реальный R@1 лежит
  в полосе 0.70–0.80: запросы порождены из тех же полей, что индексируются (завышает),
  но 62% хвостовых промахов — кривая разметка эталона (занижает).
* **Опечатки не измерены.** Сгенерированные запросы чистые. Если вход идёт от LLM
  по расшифровке — так и будет; при ручном вводе оператора нужен триграммный индекс.
* **Нагрузка по области выше потолка одной машины.** 383 окна, при 30% загрузки это
  ~29 поисков/с против 15. Нужен ONNX/int8 на энкодер, GPU или кэш.

## Переиспользование на другом корпусе

Доменно-специфичны четыре места, остальное переносится как есть:

1. **`corpus.MUNI_FULL` и `facets.STRONG/WEAK`** — газеттир территорий. Должен быть
   **один на весь проект**: у гейта была своя копия без нормализации ё, и «Щёкино»
   молча не распознавалось.
2. **`corpus.split_municipality()`** — правила вынесения фасета из заголовка.
3. **`clarify.FACETS` и `clarify.TOPIC`** — грани, по которым имеет смысл спрашивать,
   и заранее написанные формулировки вопросов.
4. **`extraction_schema`** — enum'ы предметной области.

Всё остальное — `search_text`, RRF, гейт по разрыву, `rescore`, резолв по фасету —
от домена не зависит.
