# Что мы сделали с данными и зачем

Хронология решений по данным, с числами, которые их обосновали. Отдельно —
то, что попробовали и отвергли: это экономит время следующему, кто захочет
«очевидно улучшить».

Исходник: `data/services_for_llm.json` — 732 карточки услуг МФЦ Тульской области,
плюс `db_knowledge_clean.json` и `flat_classification_clean.json` (филиалы, категории).

---

## 1. Муниципалитет вынесен из вектора в колонку

**Что нашли.** 445 карточек из 732 — одна и та же муниципальная услуга,
размноженная по 26 муниципальным образованиям. Различаются одним словом:
`«…расположенных на территории муниципального образования (Алексин)»` и названием
администрации. Крупнейшая группа — 26 карточек.

**Почему это ломает поиск.** Плотный вектор сжимает 200-токенное название в 1024
числа; один топоним при таком сжатии почти не меняет направление вектора. Замерено
на исходном индексе:

| | |
|---|---|
| медианный разрыв косинуса top1−top2 внутри группы | **0.0021** |
| тот же разрыв, p90 | 0.0115 |
| средний косинус внутри группы | 0.83–0.88 |
| документов, у которых ближайший сосед ближе 0.90 | 394 (54%) |

Разрыв 0.002 ниже разброса самой модели между запусками. Для 60% корпуса
«какая карточка первая» — подбрасывание монеты.

**Что сделали.** `corpus.split_municipality()` вырезает топоним из заголовка и из
названия администрации, кладёт в колонку `municipality`. Поиск идёт по типам,
карточка достаётся фасетом после ранжирования.

**Результат.** 732 карточки → **318 типов**. 291 тип (91%) однозначен — карточка
одна, фасет не нужен вообще. Остальные 27 типов держат 442 карточки.

**Грабля.** Первая версия правила пропустила 2 карточки из 445, где топоним стоял
не в скобках в конце, а в середине названия. Проверять так: одиночный тип, чьё
название на 75% совпадает с типом из 25+ карточек — это протечка.

## 2. `type_id` — стабильный хэш, а не порядковый номер

Сначала тип получал номер по позиции в отсортированном списке. При уточнении правил
дедупликации (318 вместо 322 типов) **все номера сдвинулись**, и сохранённый эталон
стал указывать не на те услуги — метрика упала с 0.68 до 0.04 без единого изменения
в поиске.

Теперь `type_id = blake2b(канонический ключ)`. Эталон при этом резолвит цель **через
id карточек**, а не через `type_id` — id карточек приходят из исходных данных и стабильны.

## 3. Карточки НЕ схлопнуты в хранении

Возник вопрос: раз карточки почти одинаковые, может слить их в одну запись?
Проверили поле за полем, вычистив топонимы:

| поле | расходятся ли ФАКТЫ (суммы, сроки) |
|---|---|
| `paymentInfoText` | 0 из 28 групп |
| `documentsText` | 0 из 28 |
| `serviceRecipients` | 0 из 28 |
| `serviceResultText` | 0 из 28 |
| `rejectReasonsText` | 0 из 28 |
| **`timeTermText`** | **26 из 28** |

Попарное сходство внутри группы — 0.53 по документам, 0.58 по срокам: тексты разные,
содержание одно. Пример из группы «Присвоение адреса» (26 карточек, 16 формулировок):

```
×4  «в срок не более чем 5 рабочих дней»   ─┐
×4  «в срок не позднее 5 рабочих дней»      ├─ одно и то же
×3  «в течение 5 рабочих дней»             ─┘
×3  «в срок не более чем 6 рабочих дней»    ← А ВОТ ЭТО реально другое
×1  «не позднее 7 рабочих дней»             ← и это
```

**Вывод.** Схлопывать целиком нельзя — потеряются сроки, они свои у каждого МО.
Правильная форма — «общая часть + дельта»:

* **один раз на тип:** название, документы, заявители, результат, отказы, плата;
* **на карточку:** срок, администрация, id, филиалы.

Индекс схлопнут, хранение — нет: все 732 карточки лежат целиком в `service.payload`.

## 4. Переписан текст, который идёт в вектор

**Что было.** Склейка восьми полей подряд, включая шаблон.

| поле | что в нём | различимость |
|---|---|---|
| `paymentInfoText` | «Бесплатно» | 95 значений на 711 |
| `serviceOrderingText` | «Администрация МО · МФЦ · ЕПГУ» | топ-3 = 35% |
| `departmentName` | для 445 карточек это и есть вынесенный фасет | 55 на 729 |
| `timeTermText` | сроки, для поиска не нужны | — |
| `lifeSituationNames` | язык гражданина — **стояло последним** | — |

**151 документ из 732 (21%) обрезался на 512 токенах.** Из 363 карточек с заполненным
`lifeSituationNames` у **104 (29%)** это поле отрезалось целиком — именно там, где
оно помогло бы больше всего.

**Что стало.** В вектор идут: название → синонимы → жизненная ситуация → кому →
результат → документы. Шаблон выброшен, порядок по убыванию сигнала.

Медиана **265 токенов**, p90 335, максимум 425 — **обрезается ноль документов**.

**Эффект:** R@1 0.591 → 0.628 на той же модели BGE-M3. Смена только представления
дала больше, чем любая смена модели в исходном отчёте.

## 5. Добавлены «простые названия» услуг

**Зачем.** Половина запросов не имеет ни одного общего слова с официальным названием.
«Сдать дом в эксплуатацию» и «Выдача разрешений на ввод объектов в эксплуатацию при
осуществлении строительства, реконструкции объектов капитального строительства» —
это про одно и то же, но словари не пересекаются.

**Как.** `eval/generate_aliases.py` — локальная LLM, по 4 «человеческих» названия на
каждый из 318 типов, один раз оффлайн. Кладутся в текст документа строкой
`Люди говорят: …`.

**Эффект:** R@1 0.680 → **0.732**, R@10 0.961 → 0.977.

**Проверка на циркулярность.** Запросы и синонимы породила одна модель — есть риск,
что они просто совпали словарём. Разбили замер:

| | без общих слов с названием (n=347) | с общими (n=343) |
|---|---|---|
| без синонимов | 0.591 | 0.770 |
| с синонимами | **0.651** (+6.0) | 0.813 (+4.3) |

Прирост **больше на трудном срезе** — подпись настоящего эффекта. При утечке словаря
выигрыш был бы равномерным или смещённым в лёгкий срез.

**Важно:** рукописная таблица из ~20 шаблонов давала **−0.8 п.п.**, то есть вредила.
Дело не в идее, а в покрытии: нужны все 318 типов, а не популярные случаи.

## 6. Собрана таблица предикатов права

**Что нашли.** Поле `rejectReasonsText` («основания для отказа») выглядит как то,
что нужно для проверки права. Разобрали содержимое 685 заполненных карточек:

| | доля |
|---|---|
| процедурные основания (нет подписи, нечитаемая копия, не та форма) | **51%** |
| «оснований для отказа в приёме не предусмотрено» | ~40% |
| **основания неправа** | **~1%** |

Это ответ на вопрос «почему не примут документы», а не «кому не положено».
Где условия живут на самом деле:

| поле | условий по возрасту | по льготной категории |
|---|---|---|
| **`serviceRecipients`** | **28** | **97** |
| `serviceTitleText` | 5 | 68 |
| `rejectReasonsText` | 7 | 23 |

**Что сделали.** `eval/generate_predicates.py` — LLM оффлайн строит типизированную
таблицу из `serviceRecipients` + названия:

```json
{"subject": "applicant", "field": "category", "op": "in",
 "value": ["СВО"], "quote": "принимающие участие в специальной военной операции"}
```

Получилось **363 предиката** на 318 типов, условия есть у 103 типов.

**Почему обязателен `subject`.** Прежняя версия на регулярках не различала, к кому
относится условие: «ребёнка в возрасте до 17 лет» срабатывало на возраст **заявителя**.
Из 363 предикатов **39 относятся к ребёнку, 1 к супругу** — это ровно те ложные
срабатывания. В проверку идут только `applicant`.

**Почему обязательна цитата.** Предикат отбрасывается, если цитата дословно не
встречается в исходнике — защита от выдуманных условий. И оператор показывает клиенту
строку регламента, а не пересказ.

**Предикаты одного поля — альтернативы, разных — совокупность.** Без этого услуга
«для военнослужащих ИЛИ участников СВО» оказывалась недоступна вообще никому.

## 7. Подключены филиалы

`flat_classification_clean.json` содержит 114 филиалов с адресами, графиками и числом
окон; `db_knowledge_clean.json` — связь услуга↔филиал (80 904 пары).

**Филиал бесполезен как фильтр поиска:** медианный филиал оказывает **708 услуг из
732**. Зато он знает свой район — а район это и есть фасет, по которому выбирается
карточка. Распарсили адреса: **113 из 114** филиалов маппятся на МО (25 из 26
покрыты, в р.п. Славный филиала нет).

Оператор в отделении №28 в Щекино не печатает слово «Щекино» — карточка выбирается
сама. Заодно из тех же данных получили **383 окна по области** — это знаменатель для
расчёта нагрузки на LLM.

## 8. Извлечены структурные поля

`canon.term_days` и `canon.is_free` — срок в рабочих днях (распознан у 626 из 732)
и признак бесплатности (626 из 732). Для поиска не нужны, нужны для фильтров

и для схлопывания хранения в «общую часть + дельту».

## 9. Построен набор для замеров

**Проблема исходного набора.** 16 запросов на 10 карточек. Один запрос = 6.25 п.п.,
95% бутстрап-интервал R@1 — **±25 п.п.** Все семь конфигураций исходного отчёта
статистически неразличимы; «0.62 против 0.81» — это три запроса, p≈0.21.

**Ошибки разметки, которые нашли:**

* `(«хотим подать заявление чтобы расписаться», "rast_brak")` — `rast_brak` это
  **расторжение** брака. «Расписаться» означает **заключить** брак. Модели отвечали
  правильно и получали за это штраф; вывод исходного отчёта про «разговорную омонимию»
  измерял не модель, а метку.
* «Справка о размере пенсии» размечена одним gold там, где валидны две карточки.
* «Выплата при рождении» разбита на «получение» и «распоряжение» — обе верны.

Одно исправление меток подняло исходный прод с R@1 0.625 до 0.750.

**Что построили.** `eval/generate_queries.py` — локальная LLM пишет по три запроса
«от лица гражданина» на каждый тип: вопрос своими словами, короткий запрос из 2–4
слов, описание жизненной ситуации. Получилось **690 запросов на 230 типов**,
интервал сузился до ±3.5 п.п.

**Честная оговорка.** Запросы порождены из полей карточки, поэтому абсолютные
значения завышены. Встречное смещение: прогнали все 78 промахов через LLM-судью —

| вердикт | доля |
|---|---|
| эталон прав, поиск ошибся | 38% |
| **поиск прав, эталон кривой** | 36% |
| обе годятся, эталон неполон | 17% |
| запрос мусорный | 9% |

**62% «промахов» — не ошибки поиска.** Два смещения тянут в разные стороны; реальный
R@1 лежит в полосе **0.70–0.80**, и сузить её без живого лога нельзя.

## 10. Диалоги и эталон дрейфа состояния

`eval/generate_dialogs.py` — 16 синтетических диалогов оператор↔клиент (311 реплик),
где факты выдаются постепенно. `eval/measure_churn.py` прогоняет полное извлечение
признаков на каждой реплике и смотрит, как часто найденный факт исчезает или подменяется.

**Что обнаружили.** 68% значений приходили вне схемы: `life_situation: "worker on
production"` (по-английски), `categories: "выплата"`, `life_situation: "арендатор
земли"`. Перечисление enum'ов словами в промпте LLM игнорирует. Каждый ход модель
выдумывала новую формулировку — отсюда дрейф.

| | факт исчез | значение заменено |
|---|---|---|
| свободный JSON | 5.8% | **53.7%** |
| + `validate()` по enum | 1.9% | **7.4%** |
| + `DialogState` (монотонность) | **0.0%** | 7.7% |

**Валидация снимает 89% дрейфа.** Отсюда `extraction_schema.JSON_SCHEMA` для
grammar-constrained decoding и `validate()` как страховка на приёме.

## Что попробовали и отвергли

| приём | результат | почему |
|---|---|---|
| **Гибрид с BM25 «всегда включён»** | R@1 0.631 → **0.586** | язык гражданина и канцелярит почти не пересекаются словарём; равновесный RRF тянет вниз. Полезен только по гейту разрыва top1−top2 |
| **Канонизация текста** (слияние формулировок, снятие шаблона) | всё в пределах ±3.5 п.п. | IDF в BM25 уже занижает шаблонное слово в 5–50 раз сам: `документ` весит 0.11, `газ` — 5.36 |
| **Отдельные векторы названия и тела** | 0.676 против 0.670 | шум; весь сигнал в названии, тело в одиночку даёт 0.456 |
| **Синонимы в плотный текст рукописной таблицей** | −0.8 п.п. | покрытие 20 шаблонов вместо 318 типов |
| **Гейт «звать LLM только на информативных репликах»** | ловил 63% информативных | терял **37% фактов** ради 47% экономии. Удалён |
| **Проверка права силами LLM в рантайме** | 14% самопротиворечий, 17% ложных отказов, 2.7 с на услугу | 9B меняет вердикт от перестановки фактов в промпте при greedy-декодировании |
| **Жёсткая фильтрация по ответу на наводящий вопрос** | 0.775 против 0.810 | выбрасывает цель навсегда, если признак услуги не заполнен; нужно переранжирование |

## Две ошибки в собственных замерах — чтобы не повторить

1. **«Деградация после двух вопросов».** Запросы, у которых вопросы кончились,
   засчитывались как провал на последующих шагах. С переносом результата картина
   монотонная: 0.732 → 0.778 → 0.810 → 0.829 → 0.839. Вывод был обратный правде.
2. **«23% нестабильности LLM».** Смешал перестановку фактов с температурой 0.7.
   Раздельно: температура 17–18%, перестановка 2% у 4B и 14% у 9B. Первое лечится
   настройкой декодера, второе — нет.

Мораль обе одинаковая: прежде чем объяснять неожиданный результат, проверь, не
меряешь ли ты артефакт собственного кода.
