# gpu-gateway — три модели за одним портом

ASR (GigaAM-v3 + Silero VAD), эмбеддер (mE5-large-instruct) и LLM (Qwen3.5 FP8
через vLLM) на одной арендованной карте. Сервис **не хранит состояния и не знает
бизнес-логики**: ни сессий, ни диалогов, ни корпуса услуг. Всё, что переживает
рестарт, живёт в core-api на основном сервере.

Контракт — `../api/gpu-gateway.yaml`. Архитектура целиком — артефакт
«Голосовой поиск услуг МФЦ».

---

## Модель: почему именно этот квант

**Официального FP8 у Qwen для 3.5-9B не существует.** Есть `Qwen/Qwen3.5-9B`
(18 ГБ bf16) и `Qwen/Qwen3.5-9B-Base`. Восемнадцать гигабайт в 24 не помещаются
вместе с KV-кэшем, ASR и эмбеддером.

По умолчанию берётся **`RedHatAI/Qwen3.5-9B-FP8-dynamic`** — 13.0 ГБ.
RedHatAI это бывшая Neural Magic: они пишут `llm-compressor` и заметную часть
кода квантования в самом vLLM, формат `compressed-tensors` родной для движка.

Тринадцать, а не девять с половиной, потому что **зрительная башня намеренно
не квантована** — в `quantization_config.ignore` перечислены `model.visual.blocks.*`.

## Модель мультимодальная, и это стоит памяти дважды

У `Qwen3.5-9B` есть `vision_config` — 27 слоёв зрения. Картинки нам не нужны
никогда, но отключать их надо не ради гигабайта весов.

При старте vLLM профилирует пиковую память на фиктивном запросе, и для
VL-модели подставляет туда картинку максимального размера. Оценка активаций
раздувается, и **KV-кэш ужимается ещё до первого посетителя**. Поэтому
в запуск идёт `--limit-mm-per-prompt {"image":0,"video":0}` — тогда
профилирование считается по тексту.

## Бюджет видеопамяти

Архитектура: 32 слоя, 4 KV-головы, **head_dim 256** (вдвое больше обычных 128),
`max_position_embeddings` 262144 — отсюда обязательный `--max-model-len`.

KV на токен = 2 × 32 × 4 × 256 = 65 536 значений, то есть **64 КБ в fp8**
и 128 КБ в bf16.

| 4090, 24 ГБ | ГБ |
|---|---|
| веса FP8-dynamic | 13.0 |
| GigaAM + эмбеддер | ~1.6 |
| контексты CUDA и графы | ~1.5 |
| **остаётся под KV** | **~7.9** |

7.9 ГБ при 64 КБ на токен — около **129 тысяч токенов**, порядка 60 диалогов
по 2000 токенов контекста. Для пилота на 10–20 сессий запас втрое.

**Долю считает сам шлюз**: из полной памяти вычитается 7 ГБ под ASR, эмбеддер
и запас. На 24 ГБ выходит 0.71, на 32 ГБ — 0.78. Переопределяется `GPU_UTIL`.

## nvcc в рантайме — не прихоть

FlashInfer не держит готовых ядер под все комбинации. Для sm_89 + KV в `e4m3`
+ head_dim 256 готового нет, и он компилирует ядро **при старте**. Без
компилятора под падает на `/usr/local/cuda/bin/nvcc: not found` — так и было
на первом запуске.

В образе стоят `cuda-nvcc-13-0` и заголовки CUDA; переходить на базу `devel`
ради этого дорого. Результат компиляции кэшируется, и кэш уведён на том
(`/root/.cache` → `/workspace/.cache`) — иначе минуты компиляции повторялись бы
при каждом запуске пода.

## Необязательные флаги снимаются сами

Если движок не поднялся, шлюз снимает флаги по одному и пробует снова,
записывая на странице статуса, какие снял. Два пути:

* имя флага названо в ошибке (`unrecognized arguments`) — снимается оно;
* имени нет, движок принял аргументы и умер позже — снимаются по убыванию
  риска: `--kv-cache-dtype`, затем `--limit-mm-per-prompt`, затем
  `--enable-prefix-caching`.

Второй путь появился после реального отказа: vLLM принял `--kv-cache-dtype fp8`
и упал уже на инициализации движка, когда FlashInfer полез за компилятором.
Прежняя логика, ждавшая слов «unrecognized arguments», не сработала.

## Шаблон RunPod

| Поле | Значение |
|---|---|
| Template type | **Pod** |
| Compute type | **GPU** |
| Container image | `reassel/mfc-gpu-gateway:runpod-v2` |
| Container start command | **оставить пустым** — в образе есть `ENTRYPOINT` |
| Expose HTTP Ports | `10100` |
| Expose TCP Ports | `22` |
| Container Disk | 40 ГБ |
| Volume Disk | 50 ГБ, точка монтирования `/workspace` |

Переменные окружения:

| Key | Value | |
|---|---|---|
| `GW_TOKEN` | длинная случайная строка | иначе токен генерируется при первом старте и меняется при пересоздании пода |
| `LLM_MODEL` | необязательно | если автоподбор репозитория ошибётся |
| `GPU_UTIL` | необязательно | переопределить автоподбор доли видеопамяти |
| `HF_TOKEN` | необязательно | если репозиторий модели окажется закрытым |

`PUBLIC_KEY` RunPod подставляет сам из ключа в вашем аккаунте; entrypoint
поднимет sshd, только если переменная пришла.

**Переменные vast.ai не нужны.** `OPEN_BUTTON_PORT`, `OPEN_BUTTON_TOKEN`,
`JUPYTER_DIR`, `DATA_DIRECTORY`, `PORTAL_CONFIG` относятся к порталу vast
и на RunPod не делают ничего. Порты 1111, 6006, 8384, 10200, 72299 — оттуда же.

Веса кладутся в `/workspace/hf`, то есть на том: пересоздание пода не заставит
качать их заново.

### Сборка образа

```bash
DOCKERHUB_USER=<логин> ./build_push.sh runpod-v2
```

На Apple Silicon сборка идёт через эмуляцию QEMU — около получаса; на x86-64
Linux минут пятнадцать. Нужно порядка 50 ГБ свободного места: кончится
на середине — buildkit упадёт с `input/output error`.

## Проверка сборки

```bash
python3 /opt/mfc/smoke.py --token "$GW_TOKEN"
```

Шаг 1 плана — то, что может отменить всё остальное. Три несущих допущения
в порядке убывания риска:

| | что подтверждаем | цена ошибки |
|---|---|---|
| 1 | vLLM с FP8, GigaAM и sentence-transformers уживаются на sm_120 и влезают втроём в 32 ГБ | план несостоятелен целиком |
| 2 | движок принимает JSON-схему (`guided_json` или `response_format`) | дрейф значений 54% вместо 7% |
| 3 | кэш префикса работает: `cached_prefix_tokens` растёт вместе с диалогом | префилл ×40, одна карта не тянет даже пилот |

Плюс замеры: задержка ASR на сегмент, эмбеддинг строки и батча, извлечение
фактов по ходам растущего диалога, вопрос по документу со сверкой цитат.
Данные берутся из репозитория — `eval/dialogs.jsonl`, `services_for_llm.json`,
`Test audio/output.wav`. Ненулевой код возврата, если провалена хоть одна
несущая проверка.

## Настройка

| переменная | по умолчанию | |
|---|---|---|
| `GW_PORT` | `10100` | единственный порт наружу |
| `GW_TOKEN` | генерируется в `/workspace/.gw_token` | пусто = авторизация выключена |
| `VLLM_PORT` | `8901` | только 127.0.0.1, наружу не выставляется |
| `LLM_MODEL` | резолвится перебором | задать явно, если автоподбор ошибся |
| `GPU_UTIL` | `0.72` | доля VRAM под vLLM; остаток — ASR и эмбеддер |
| `MAX_LEN` / `MAX_SEQS` | `16384` / `32` | контекст и параллельность |
| `EMB_MODEL` | `intfloat/multilingual-e5-large-instruct` | **менять только вместе с перестройкой индекса** |
| `ASR_VARIANT` | `e2e_rnnt` | или `e2e_ctc` |

Префикс `Instruct: …\nQuery: ` задаётся **только** в `config.py` и применяется
сервером по полю `kind`. Если вызывающий код начнёт добавлять префикс сам,
индекс и запрос однажды разъедутся молча — цена на этом корпусе измерена
и составляет −19 п.п. R@1.

## Схема извлечения — копия, а не форк

`gateway/vendor/` содержит копии `extraction_schema.py` и `facets.py` из
`embending/v2/`: шлюз едет на машину без корпуса услуг, импортировать оригинал
неоткуда.

```bash
./sync_vendor.sh          # обновить копии и контрольные суммы
```

Суммы отдаются в `GET /v1/models` (`vendor_sha256`); core-api сверяет их при старте.

## Тесты

```bash
python3 -m pytest tests -q
```

Восемь проверок того, что ломается **молча**: промпт извлечения только
дописывается, перечисления присутствуют дословно, документ идёт раньше вопроса,
префикс входит в отпечаток, выдуманная цитата не доходит до оператора,
смещения цитат указывают в исходный текст поля. Ни одна из этих поломок
не вызывает ошибки — они просто тихо ухудшают продукт.

## Если что-то пошло не так

Сначала — страница статуса: там видно, на какой фазе встало и что в логе.

| симптом | что смотреть |
|---|---|
| фаза «Веса LLM» красная | `resolve_model.py` не нашёл репозиторий — задать `LLM_MODEL` явно |
| фаза «Запуск vLLM» красная с OOM | снизить `GPU_UTIL` до 0.65 и `MAX_SEQS` до 16 |
| «Процесс vLLM: не запущен» | хвост лога vllm на той же странице |
| `struct_mode` пустой или `none` | движок не принял схему; проверить версию vllm |
| загрузка встала на весах | кончился диск: пересоздать инстанс со 100 ГБ |
| torch подменился в фазе 2 | скрипт переустановит vllm сам; если повторяется — зафиксировать версию torch в `requirements.txt` |
